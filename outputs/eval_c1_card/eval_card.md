# Eval 评测卡 — C1 同批往返（codec 重建上限基线）

- 评测对象：EnCodec 24kHz/24kbps，n_q=32 / 75Hz / 码本 1024，transformers 5.16.1
- 数据域：seedlib 参考音 n=95；B 站实战切片 n=96（同批、同一 log-mel 实现、一次跑完）
- gt 分支：`orig`（原始输入）；候选：`L16`（16 层 12kbps）、`L32`（32 层 24kbps）
- 指标：log-mel L1（越低越好，相对 orig）、hf|Δ|（高频能量占比绝对差，仅参考不入 gate）、decode 长度比
- 复算方式：由 Eval 从 `report.csv` 逐条独立重算，未引用 Codec 汇总值；重算结果与其报告逐项一致

## 反证与不可过度解读

1. **HF 占比 L32 并非普遍更好**：snares 9/22、hihats 4/8、实战 cymbal 7/12、实战 hihats 8/12 反退。稳定改善只出现在 mel L1。
2. **域差距真实存在**：snares seedlib 0.6090/Δ6.3%（通过）vs 实战 0.8284/Δ3.4%（不通过）；hihats Δ% 两域 3.4 vs 7.3。任何“已改善”结论必须写明域。
3. 本表只评 **codec 重建上限**，gt 为有损重建；生成模型的误差需在此基线之上另算（模型误差 = 生成 vs L16/L32 重建，不得与 orig 直接比）。

## QC 发现（A/B 前必须处理）

1. **pack 与 report 不一致**：`outputs/c1_real/pack` 实际 417 个 wav（139 组三列），report/manifest 只有 96 条；43 组三元组未入表但已写出（同一时间窗）。Codec 报告中的“288 个 wav”与实际不符。→ A/B 的 gt 分支需按 report 的 96 个 ref_id 过滤，或由 @Codec 说明这 43 组的身份。
2. **12-of-N 挑选规则未留痕**：real 域 8 个 family 各有约 17 个候选（来自 `data/real_bbox/hybrid_labels_all_highconf_l2.jsonl`），入表各 12 条，manifest 未记录挑选/随机种子。存在挑选偏差风险，请 @Codec 补规则；补不上就把这 139 组全部入表重算（我可复算）。
3. `c1_encodec` 侧干净：285 wav = 95×3，pack id 与 report 完全一致；tokens 95 个 npz。
